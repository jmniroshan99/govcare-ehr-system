ROOT CAUSE

The old Renal Trends chart used a dialysis-specific observation list plus a
separate CKD feature history. Its source count represented renal-session rows,
not all laboratory evidence. The feature projection did not read lab_results,
CBC report results or standalone stored FHIR observations. It also lacked an
explicit verification flag for graph eligibility. A large chart container and
generic zero-lab wording obscured these differences.

Read-only audit of this local PostgreSQL database found:
  Verified renal-session rows:                      0
  Saved CKD assessments / feature projections:     41 / 41
  FINAL clinical observations:                    748
  FINAL clinical observations without collection: 726
  Verified manual-entry records:                   0
  Active laboratory results:                      18
  Laboratory results with verification/collection: 1
  CBC reports:                                     0
  Stored FHIR Observation resources:              284

These are database-wide counts, not counts for the unidentified patient in the
original screenshot. No screenshot-patient identifier was supplied. The evidence
supports both an incomplete source query and genuinely missing collection dates;
it does not establish which records belong to that screenshot patient.

The exact three production clinical/laboratory/FHIR SQL queries were also run
read-only against a local patient with clinical history. They returned 47, 0 and
11 rows respectively. Evidence contains counts only, without patient identifiers
or clinical measurements. This check verifies SQL execution, not API RBAC.

The section now provides patient/status/evidence metadata, five verified result
cards, dated Recharts graphs, measurement and time selectors, refresh, existing
clinical-entry dialogs and a source-history table. Serum, pre-HD and post-HD
measurements retain separate series or an explicit sampling-context selector.
One result renders as one point. Zero results produce compact instructions and
graph-readiness progress. Assessment values without source verification appear
separately. A failed API request produces a recoverable error rather than zero
patient data. Patient switching aborts requests and closes old patient dialogs.

Spring and normalization:
  ClinicalPredictionFeatureService.java discovers existing CKD projections,
    clinical observations, laboratory results, CBC results and FHIR quantities,
    including panel components. ClinicalPatientAccess remains the scope boundary.
  ClinicalFeatureNormalizer.java retains entry source and explicit verification.
    Additional chemistry definitions normalize supported explicit units.
  RenalTrendTimeline.java builds a read-only provenance-aware timeline with
    inclusion decisions, missing-date/unit/verification reasons, duplicate
    suppression, conflict exclusion and distinct sampling contexts.
  ClinicalFeatureMappingEngine.java attaches that timeline to the existing
    six-module response and persisted snapshot.
  RenalClinicalModuleService.java excludes evaluation time from the fingerprint
    so refreshing an unchanged timeline does not itself create a new snapshot.
  PredictiveIntelligenceService.java reuses the existing verified-entry, audit,
    idempotency and FHIR Observation/Provenance workflow for generic whole urea,
    albumin, sodium and calcium. Whole urea remains distinct from BUN.

No database migration was needed. Existing JSON and observation tables already
support this capability. No FHIR resource schema or ML artifact was replaced.
Queries remain hospital/patient scoped. FHIR FINAL status alone does not confer
source verification. Existing linked clinician-verification records provide the
verification evidence; unresolved imported FHIR values remain excluded.

FORECASTS

React continues to use Spring only. Existing authenticated Spring-to-Django
inference, stored prediction snapshots, review and FHIR write-back remain intact.
The chart uses stored Hb/URR outputs only when the existing backend module permits
the forecast. A dashed overlay additionally requires compatible units, an actual
origin matching a measured point and an explicit later target date. No frontend
3-, 6- or 12-month forecast is manufactured. Backend next-observation horizon text
is displayed unchanged. Research estimates carry NOT CLINICALLY VALIDATED.

Model details, requirements, explanation, associated features, supplied interval,
source snapshot and review reference are expandable. SHAP contribution units are
read from the serving output; they are not described as clinical risk percentages.
Hyperkalemia remains a separate research score in the existing modules, never a
diagnosis or a potassium measurement.

KNOWN LIMITATIONS

The source screenshot patient cannot be identified from the supplied request.
Source verification and collection dates cannot be reconstructed from missing
evidence. The system deliberately leaves those values outside verified graphs.
Legacy assessment snapshots without verification metadata remain separate from
verified laboratory history. Old PDF snapshots require a newly captured current
workspace snapshot to acquire the new verified timeline.

Browser screenshots use operational fixtures, including a model-unavailable
scenario; they do not establish the native installation's model availability.
Clinical validation and dataset permission status remain as reported by existing
model governance. No forecasts or probability values were inserted into patients.

The required 12ui design service was attempted but requires account sign-in.
The implementation uses existing GovCare tokens/components. The report does not
claim a completed 12ui design comparison.

  cd spring-api; mvn test
  .venv-cdss312/Scripts/python.exe ML_Server/manage.py test renal_service

Browser: run RenalTrendTimelineTest to generate fixtures, start Vite, set
GOVCARE_VISUAL_URL, GOVCARE_PLAYWRIGHT_MODULE and GOVCARE_CHROMIUM_EXECUTABLE for
your local browser tools, then run scripts/verify-renal-trends-browser.mjs.
The default width list is all three requested widths.

Native read-only checks: set GOVCARE_TRENDS_API to the Spring origin and, if
needed, GOVCARE_TRENDS_ACCOUNTS to a valid private test-account JSON file; run
scripts/verify-renal-trends-live.mjs. Ordinary overview access writes the existing
audit/module snapshot records; the verifier does not add clinical measurements
or run predictions.
